# World Liquor 0.1.172

Pochi Pudding remainder parity with Java `CompatFoodItem.finishUsingItem` (NeoForge 1.21.1 author 1.1.11 / CF9066406). `super.finishUsingItem` applies the food effects and consumes one serving unless the player has infinite materials; if the used stack became empty the item returns a new Bowl and `LivingEntity.completeUsingItem` places it in the used hand, otherwise — including Creative — one Bowl is `spawnAtLocation`'d at the entity and the original stack stays. Until now the Bedrock port always inserted the bowl into the inventory.

`runtime/BP/scripts/food-remainder.js` owns the remainder table (only the pudding carries one) and the two Java branches. Because native food debits its own stack around the `onCompleteUse` callback, the branch is decided one tick later from the same selected slot: an empty slot receives the bowl in hand; the same pudding still there (servings left, or Creative which never debits) drops one bowl at the player's current position; anything else in that slot means the player moved items during the tick, so the bowl goes through the existing Java `Inventory.add` ordering rather than overwriting their item or vanishing. Abilities are sampled at completion, like Java. Unresolved cases (player left, rejected drop, unreadable inventory) are recorded in `foodRemainderDiagnostics` and never retried or written twice. The superseded `returnItem` inventory insertion is removed.

`tests/food-remainder.test.mjs` covers the last serving, servings left, Creative with and without an engine debit, abilities sampled at completion, a changed slot, a full inventory, a renamed pudding, a departed player, a rejected drop and the registered `kaleidoscope_world_liquor:food` callback dispatching effects before scheduling. These are API-model cases: the actual native debit/callback order, the Survival/Creative bowl destination and the dropped item's position on a real client remain acceptance scenarios (see BUGS and PARITY-MATRIX). Luck and the author's random-draw sequence are unchanged and still open.

No other gameplay, recipes, resources, UUIDs or Tavern dependencies change. Client acceptance stays pending and `production_ready=false`.
